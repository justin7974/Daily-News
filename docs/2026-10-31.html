开源模型的网络安全风险：漏洞发现提速，修补能力成为约束
Nathan Lambert 修正了自己此前把开放权重网络安全风险称为“还好”的措辞：他仍不认为风险已出现灾难性跃迁，但承认软件行业将被迫经历昂贵的升级。文中援引 Epoch AI 用 GLM-5.3 构造 Firefox 攻击的实例，指出发现漏洞与形成实际危害之间仍有部署、诱导访问等环节。作者认为，当前证据不足以把新增攻击主要归因于开源模型，闭源模型同样参与其中。他还提醒，大型开放模型短期内受服务成本和算力供给限制，防守方能否及时采用、修补才是关键变量。
🦐点评：Lambert 提到 GLM-5.3 已能串起实际攻击，这会让“又发现多少漏洞”的产品指标迅速贬值。安全创业公司更该证明从可利用性验证到补丁上线能缩短多少时间；能接进客户发布流程、明确修复责任并验证结果的团队，才有机会把模型能力转成持续预算。

a16z 重审创始人画像：AI 降低开发门槛，也抬高种子轮交付标准
Andrew Chen 认为，AI 将扩大单人、非技术背景、行业专家、年轻人和内容创作者的创业机会，但逐一列出了这些画像的短板。单人能做更多事，合伙团队也会同步提效；能做原型，距离可靠、可扩展产品仍有技术判断的差距。行业经验可能帮助发现问题，也可能限制颠覆性思考；自带粉丝能带来首发流量，却不能替代长期增长。文章进一步指出，热门创始人画像既来自技术与分发优势，也会因投资人共同偏好而获得自我强化的融资优势。
🦐点评：Chen 提到创作者的分发和行业专家的经验，真正该追问的是这些资产在 AI 普及后还剩多少稀缺性。早期筛选可以少用“是否技术合伙人”做一票否决，多看创始人能否拿到独有客户反馈、修复真实失败并持续成交；演示普及后，这些证据应更早进入种子轮门槛。
a16z.news
17 位 AI 100 创业骨干转入隐身项目，人才流动提供早期寻源线索
CB Insights 从历届 AI 100 公司中识别出 17 位正在隐身创业的创始人及早期团队成员，并结合履历、论文和公开发言推测新方向。Jina AI 联合创始人 Bing He 自述探索 Agent 与硬件；Chai Discovery 前创始科学家 Zhuoran Qiao 透露建设覆盖分子设计到制造的化学基础 AI。Ema 前创始工程师 Amitha Gopidi 所在医疗科技项目自述已在两家诊所试点。名单也覆盖空间智能、身份验证和 Agent 安全，但部分方向仍是研究机构推断，不能视作已发布产品或已确认融资。
🦐点评：Gopidi 的两家诊所试点，比“又一位明星团队成员创业”更接近可验证的投资线索。用这份名单找人后，应先核实离职时间、实际职能和客户承诺；对化学、硬件这类长周期项目，还要区分人才声誉能带来首轮融资，还是能持续带来实验资源与真实数据。
cbinsights.com
Claude Code 加强目录写入边界，企业控制进入执行与网关层
Claude Code v2.1.314 新增 permissions.blockWritesOutsideWorkingDirectories，使 Write、Edit 和 NotebookEdit 在所有权限模式下拒绝写入工作目录外路径。Claude apps gateway 可按 IdP 用户组限制上游路由，故障切换同样遵循该限制；Bedrock 上游可记录触发的 guardrail 类型而不记录匹配文本。更新还修复了恢复到 worktree 后沙箱未生效，以及部分被拦截调用看起来像已执行的问题。另有无头启动失败错误退出、管理策略刷新和超大上下文压缩等修复，均为官方发布说明。
🦐点评：Claude Code 把目录边界和 IdP 分组做进产品后，单靠给通用 Agent 加一个权限开关的公司会更难收费。独立安全层的空间应落在跨 Agent、跨应用的统一策略与执行证据上；尤其要验证 shell、MCP 和业务 API 的权限是否一致，不能把三种编辑工具的限制理解为所有操作都被隔离。
github.com
OpenAI 将支持统一 AI 训练偏好信号，网站无需逐个维护厂商规则
OpenAI 宣布将尊重 robots.txt 中供多家参与厂商共同识别的 AI 训练偏好信号，减少网站运营者逐个配置爬虫规则的负担。公司计划未来数月实施，并在落地时另行披露细节，当前仍是承诺。既有爬虫控制继续适用，新的共同信号不会替代原有规则。方案参考 IETF AI Preferences 工作组的讨论，属于自愿参与机制，公告未声称已覆盖所有模型厂商。
🦐点评：OpenAI 愿意接共同信号，会降低内容方表达选择的成本，也让纯粹代管爬虫黑名单的服务更难形成壁垒。内容基础设施公司的价值要向使用证据、授权交易与结算迁移；共同信号只能表达偏好，能否证明内容如何被使用，才更接近可收费的资产。

AI 如何改写企业安全预算？自动攻防、Agent 权限，与代码安全
海外独角兽编译的 a16z 调研覆盖 100 位 CISO，所在企业员工均超过一千人；87% 预计安全支出增加，但只有 18% 已在生产中使用 AI SOC 工具。未来十二个月，45% 计划采购或升级内部 Agent 安全产品，63% 表示安全要求已推迟或限制部分 AI 使用。采购渠道仍偏向既有厂商：44% 优先看现有平台，21% 优先找 AI 原生厂商，25% 表示不向创业公司采购。文章讨论的 Armadin、Neo 等包含 a16z 投资项目，需把采购意向、真实成交与投资方推广区分开。
🦐点评：这份调研里，进攻性安全有 42% 偏向 AI 原生厂商、24% 选择老平台附加功能，比笼统的预算上涨更能指导早期选项目。团队应先从老平台覆盖不好的持续攻击验证切入，并接上修复系统；若只做通用告警摘要，很可能在客户真正采购时输给现有供应商的捆绑报价。

开源模型亟需另开一桌
作者批评用单一综合榜单评价开源模型，认为增加推理时长换分数，可能损害真实任务体验。他以 DeepSeek 的效率路线、K3 的前端训练取舍为例，主张按工作领域和速度成本分别比较。文章宣布筹建来自真实任务、真实环境的开源 Benchmark 社区，合作评测将陆续发布。关于厂商“刷榜”及能力优劣的归因属于作者观点，文中未提供完整、可复现的横向实验。
🦐点评：若 K3 的优势来自前端专门优化，就该看设计转代码的返工率和付费复用，而不是机械地按综合分数对标 Anthropic 给估值。垂直能力可能比总榜更早变现，但也可能只适合一次性演示；两者的区别要到客户连续几周的实际任务里验证。
